# Ichiran capability and reference audit

Audit source: Ichiran `002a695b3c86a9524e49354f04b7a915beb71270`, Himotoki `eb4faf962fc0e5baf0bab22179ece1fc67fd1647`. This is a source inventory and executable comparison harness, **not a certification of parity**. The implementation evidence below reflects branch source and focused tests; implemented capabilities remain distinct from verified upstream equivalence.

> **Scope:** this audit covers the legacy engine (`packages/core/src/engine.ts`) and the published-test harness. The TypeScript port of Ichiran itself (`packages/core/src/ichiran`) and its comparisons against live Ichiran are documented in [ICHIRAN-PORT.md](ICHIRAN-PORT.md). The “Original Ichiran live oracle” section below describes the state before that oracle was built.

## Evidence types

- `tests/fixtures/upstream/ichiran-tests.json`: **published test expectations**, extracted from the pinned `tests.lisp`; source SHA-256, commit, source line and MIT notice accompany the cases. Original Ichiran was not executed to obtain them.
- 741 segmentation cases: 541 literal assertions and 200 deterministic expansions of the counter-test loops, including the upstream exception for 十一つ. Four cases contain `:gap`, which upstream substitutes for unrecognized spans, so the boundary runner excludes them rather than inventing spans. 737 cases are eligible for boundary comparison.
- Two literal `parse-number` expectations. The round-trip property over four integers remains a property in upstream source, and is listed as skipped; it is not transformed into fabricated kanji or kana output.
- **Zero romanization golden assertions in this pinned test file.** The extractor supports literal romanization assertions for future source versions, but README examples and Yomichi outputs must not be relabelled upstream tests.
- JSON consistency, 13 kanji-reading alignment assertions, number basic splitting, conjugation-database linkage and custom XML loading are present in upstream tests but are not run by this boundary harness. These remain separate coverage gaps.
- Himotoki tests/data contain additional references and properties. They are independent sources, not evidence that Ichiran itself was run. No Himotoki execution claim is made here.

The extractor uses a non-evaluating Lisp reader for strings, quote/list syntax, line comments, nested multiline block comments, and source line tracking. It expands only the pinned literal string `dolist` / two-argument `format` / equality-exception counter pattern. It does not evaluate arbitrary Lisp, interpret the full Common Lisp reader, or claim every upstream assertion has become a golden case. Focused tests cover comments, multiline forms, escaped quotes, loop exclusions and UTF-16 metrics.

## Reproduce and run

From the Yomichi repository root:

```sh
node --import tsx scripts/extract-ichiran-tests.ts ../references/ichiran tests/fixtures/upstream
node --import tsx --test tests/reference-extraction.test.ts
# Direct core/SQL validation against a fully imported dictionary (no HTTP rate limit):
node --env-file-if-exists=.env --import tsx scripts/parity.ts --database > data/parity.jsonl
# Alternatively start Yomichi against the real dictionary first:
YOMICHI_API_URL=http://localhost:3000 node --env-file-if-exists=.env --import tsx scripts/parity.ts > data/parity.jsonl
# A small diagnostic run (must not be described as full corpus validation):
YOMICHI_API_URL=http://localhost:3000 node --import tsx scripts/parity.ts --limit 20
```

The `--database` mode uses the real PostgreSQL repository and core analyzer directly, pins one repository snapshot, and closes the connection pool on completion/error. It avoids the default HTTP limit of 60 requests/minute. For full HTTP corpus runs configure a suitable isolated test server limit or pace requests externally; rate-limit failures abort the run. The optional `--corpus PATH` accepts the same provenance/cases envelope. `--predictions PATH` reads actual captured Yomichi predictions of shape `[{"id":"segment-1","text":"…","tokens":["…"],"dictionary":{"version":"…"}}]`. It is useful for offline repeatable evaluation; do not fill it by copying expectations. The runner aborts on missing/duplicate predictions, text mismatch, invalid reconstruction, HTTP errors or absent candidates rather than counting errors as passes. It reports every mismatch, data versions, evaluated count, exclusions, exact segmentation rate, and micro-averaged precision/recall/F1 over **internal** UTF-16 boundaries. Shared start/end positions receive no credit. A zero-denominator precision/recall is null. Exact boundary agreement does not establish reading, POS, sense, score, conjugation or overall equivalence. Corpus cases are not a representative held-out natural-language benchmark.

For full-dictionary validation, obtain licensed real JMdict XML/gzip; run migrations and `npm run import:jmdict -- data/JMdict_e.gz VERSION`, optionally import KANJIDIC, run `scripts/parity.ts --database` (or start `npm run dev` for an appropriately rate-limited API run), and run the 737 eligible cases without `--limit`. Record the Yomichi revision, source checksum/date, dictionary metadata, analyzer settings, full JSONL and environment. No production fixture fallback is acceptable. Dictionary version drift, known upstream expectations, alternative valid parses and implementation errors are all possible mismatch explanations. Review cases before changing grammar rules.

## Original Ichiran live oracle: precise prerequisites and status

At audit time this environment has **no `sbcl`, `psql`, or `docker` executable**. No original Ichiran live corpus was captured. The upstream Docker README's 748 passing assertions and approximately 4.7 GB restored database are upstream documentation, not measurements reproduced here.

A feasible isolated oracle needs:

1. A pinned SBCL runtime (upstream Docker uses Debian bookworm and apt SBCL), Quicklisp bootstrap, and ASDF dependencies: cl-ppcre, alexandria, split-sequence, postmodern, cxml, cl-unicode, cl-csv, lisp-unit, bordeaux-threads, jsown, lparallel, diff, cl+ssl; CLI additionally needs unix-opts. Pin their versions for a reproducible capture.
2. PostgreSQL server/client and UTF-8 Japanese locale. The pinned compose file downloads `https://github.com/tshatrov/ichiran/releases/download/ichiran-260118/ichiran-260118.pgdump`. Verify checksum and record it; do not silently use a newer release. Upstream `postgres:latest` is unpinned and should be recorded/pinned before measurement. Restore to an isolated database with disk/WAL headroom.
3. JMdictDB repository CSV/data files (upstream Docker clones `https://gitlab.com/yamagoya/jmdictdb.git` without a revision pin); record its exact commit. Alternative full initialization needs licensed JMdict, conjugation CSV inputs and optional KANJIDIC. The upstream README warns full initialization can take hours.
4. `settings.lisp` connection/path configuration, `add-errata`, cache initialization and `(ichiran/dict:init-suffixes t)`, then `(ichiran/test:run-all-tests)`. Preserve output/failures before accepting the oracle installation.
5. Capture `ichiran-cli -f -l 1 TEXT` output via argument arrays, never shell-interpolated text. Save raw JSON, executable/source/data versions, invocation and timestamps. For exact boundary comparisons derive surface spans from that raw output and verify reconstruction against the original text; upstream character indexes and Yomichi UTF-16 positions must be normalized explicitly. Label those records `live-oracle-output`, separately from the published-test fixture. The harness currently consumes normalized cases, not undocumented raw CLI JSON.

Large downloads and runtime installation were not attempted during this audit. The TypeScript production runtime remains independent of SBCL/PostgreSQL oracle deployment details.

## Recorded full-source query-index evaluation

`node --import tsx scripts/evaluate-jmdict.ts > data/parity-full-summary.json` streams the actual `data/JMdict_e.gz`, parses every entry, generates its forms with the production morphology function, and retains only forms requested by the reference corpus. The requested set includes every original/normalized substring and virtual prefixes ending in て/で for contraction lookup. The repository adapter rejects any unindexed lookup request, rather than silently treating it as an absent word. This is a **full-source dictionary scan with a bounded query-specific in-memory index**, not a full PostgreSQL import or deployment/load benchmark. No synthetic dictionary or upstream custom overlay is used.

The retained cache (`data/parity-query-index.json`) permits `node --import tsx scripts/evaluate-jmdict.ts --reuse-index > data/parity-full-summary.json` after engine/grammar-only changes. Reuse verifies the compressed dictionary, corpus and morphology hashes; morphology or dictionary changes require a new scan. `data/parity-full.jsonl` contains all compared cases and the summary, including the complete analyzer source fingerprint and engine/grammar hashes, timestamp, timings and exclusions. The local data/report files are ignored by git; this document retains the measured result and source identity.
